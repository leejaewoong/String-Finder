# L10N String ID 자동화 PoC 설계

## 1. 목적

String-Finder Windows 앱에 아웃게임 L10N 작업 흐름을 추가한다. 사용자는 Confluence 위키 페이지, 하나 이상의 Figma URL, ReleaseDate만 입력한다. 앱은 Figma의 스트링 태그를 읽고 위키의 국문·영문과 비교하여 String ID를 생성하며, 사용자가 위키에서 검토한 뒤 로컬 GDD JSON에 반영한다.

PoC는 앱이 Figma, Confluence, LLM API를 직접 호출한다. Git pull, commit, push와 사내 서버 배포는 범위에서 제외한다. 기능이 검증되면 직접 호출부를 사내 Gateway로 교체한다.

## 2. 성공 기준

- 앱 설치본에서 외부 `.env`를 통해 Figma, Confluence, LLM에 접근할 수 있다.
- Figma 스트링 태그의 노드 참조로 대상 문구와 화면 문맥을 수집한다.
- 위키에 L10N 표가 있으면 정상 항목을 비교·처리하고 불일치 항목만 건너뛴다.
- 위키에 L10N 표가 없으면 Figma 프레임 이미지와 스트링 정보를 이용해 표를 생성한다.
- 기존 키 재사용, 충돌 재번호화, COMMON 추천 규칙을 적용해 위키의 `String ID` 컬럼을 갱신한다.
- 최종 확정 시 검증된 항목만 로컬 JSON에 반영하고 변경 내역을 보여준다.
- 작업 취소, 반복 생성, 부분 오류를 안전하게 처리한다.

## 3. 앱 구조

Electron renderer는 입력, 작업 상태, 결과만 표시한다. 토큰 사용, 외부 API 호출, Figma 분석, ID 결정, 파일 변경은 main process에서 수행하고 preload IPC를 통해 renderer에 노출한다.

서비스 경계는 다음과 같다.

- 환경 설정: `.env` 경로와 필수 설정 검증
- Figma: 파일·노드 조회, 스트링 태그 해석, 타겟 문자열과 프레임 추출
- Confluence: 페이지·표 조회, 첨부 업로드, 표와 String ID 컬럼 갱신
- ReleaseDate: 제목의 버전과 업데이트 위키에서 PC 출시일 결정
- String ID: 기존 JSON 인덱싱, ID 추론, 재사용, 충돌, COMMON 판단
- JSON 반영: 변경안 검증, 백업, 쓰기, 롤백, diff 생성
- 작업 오케스트레이션: 단계, 취소, 반복 실행, 부분 오류를 관리

향후 Gateway 전환 시 renderer와 String ID·JSON 도메인 로직은 유지하고 Figma, Confluence, LLM 호출 구현만 교체한다.

## 4. 환경 설정과 비밀정보

개발 실행은 프로젝트 루트의 `.env`를 읽는다. 설치 앱은 `%APPDATA%\String-Finder\.env`를 읽는다. 실제 `.env`는 Git과 설치 파일에 포함하지 않는다. 저장소에는 값이 없는 `.env.example`만 둔다.

필수 항목:

- `FIGMA_API_TOKEN`
- `CONFLUENCE_BASE_URL`
- `CONFLUENCE_EMAIL`
- `CONFLUENCE_API_TOKEN`
- `OPENAI_API_KEY`
- `OPENAI_MODEL`은 선택이며 기존 기본값을 유지한다.

앱은 누락된 변수명과 설정 파일 위치만 안내한다. 토큰 값, 인증 헤더, 응답의 민감정보는 로그에 기록하지 않는다. 기존 Analytics 설정은 변경하지 않는다.

## 5. 인터페이스

기존 화면 상단에 `문자열 검색`과 `String ID 생성` 탭을 둔다. 확정안은 전용 화면 방식이다. `String-Finder` 헤더 아래 구분선은 두지 않고, 탭 영역 아래에서 콘텐츠를 구분한다.

입력 필드:

- 위키 URL 1개
- Figma URL 여러 개
- `RELEASE DATE`

주요 동작:

- `String ID 생성`: 최초 생성과 반복 생성을 같은 이름으로 제공한다.
- `최종 확정`: 위키를 다시 읽어 검증한 뒤 JSON을 반영한다.
- `작업 취소`: 현재 앱 작업 상태를 종료한다.

탭 이름에는 현재 상태 배지를 표시한다. 상태는 `입력 중`, `Figma 확인 중`, `표 생성 중`, `영문 검수 대기`, `String ID 생성 중`, `위키 검토 대기`, `JSON 반영 중`, `확인 필요`, `완료`, `오류`를 사용한다. 예: `String ID 생성 · 위키 검토 대기 · 확인 필요 3`.

우측 작업 상태 영역은 정상 처리, 기존 키 재사용, 신규 추가 예정, COMMON 추천, 자동 보정, 건너뛴 항목 수와 마지막 생성 시각을 보여준다. 누락·불일치 항목은 펼칠 수 있는 목록으로 앱에만 표시하며 위키에 오류 컬럼을 만들지 않는다.

`String ID 생성`은 최종 확정 전까지 반복할 수 있다. 반복 실행은 위키의 현재 값을 다시 읽는다. 사용자가 편집한 유효한 ID는 유지하고, 실제 충돌이나 COMMON 우선 규칙에 해당하는 값만 변경한다.

## 6. Figma 입력과 스트링 태그

`[L10N_NEW]` 같은 TEXT 레이어 접두어는 사용하지 않는다. 레이어명에 `스트링 태그`와 `%stringTag` payload가 있는 태그 인스턴스를 자동화 대상으로 삼는다.

관찰된 형식:

```text
03. 스트링 태그 (%stringTag^A^표시 문구^I1889:25171;8970:7176^피쳐:화면_타입_숫자)
```

payload는 `^`로 구분한 다음 항목으로 해석한다.

1. `%stringTag`: 식별 토큰
2. `A`: 위키의 구분자
3. 표시 문구: 태그 표시용 메타데이터이며 국문 원본으로 사용하지 않는다.
4. 노드 locator: 직접 노드 ID 또는 `I` 접두어가 붙은 인스턴스 내부 참조 경로
5. String ID 힌트: 피처·화면·타입 추론에 사용하는 문맥

노드 locator는 한 행의 타겟을 찾는 불투명 참조 경로로 취급한다. 세미콜론으로 나뉜 값을 여러 행으로 해석하지 않는다. resolver가 직접 노드, 인스턴스와 내부 노드 경로를 따라 실제 표시 문자열을 찾는다. 국문은 태그의 표시 문구가 아니라 타겟 TEXT의 `characters` 또는 참조 경로가 가리키는 유효한 텍스트 값에서 얻는다.

payload가 잘못됐거나 타겟을 찾지 못한 태그는 해당 항목만 `Figma 태그 오류`로 건너뛰며 다른 항목은 계속 처리한다.

## 7. 이미지 프레임 결정과 임시 파일

각 스트링 태그의 타겟 노드에서 상위 계층을 따라가며, 타겟은 포함하지만 해당 스트링 태그는 포함하지 않는 가장 바깥쪽 FRAME을 이미지 내보내기 단위로 선택한다. 여러 태그가 같은 프레임을 가리키면 프레임 이미지는 한 번만 생성한다.

예시 파일에서는 외부 `스펙 페이지`가 아니라 1920×1080의 `메인_외형 챌린지 선택` 프레임이 선택된다.

Figma URL에 선택 노드가 있으면 해당 범위에서 태그를 찾는다. 페이지 URL이면 페이지 내 유효 태그를 모두 찾고 프레임을 위 규칙으로 그룹화한다. 중복된 파일 키와 노드 범위는 한 번만 처리한다.

PNG는 `%TEMP%\String-Finder\l10n\<task-id>\`에 임시 저장한다. Confluence 첨부가 끝나거나 작업이 실패·취소되면 임시 파일을 정리한다. 사용자 폴더에는 영구 산출물을 남기지 않는다.

## 8. 위키 표 감지와 생성

페이지에 `국문`과 `영문` 헤더를 가진 L10N 표가 있으면 기존 표로 판단한다. 페이지의 다른 표는 무시한다. 기존 표에 `String ID` 컬럼이 없으면 이 컬럼만 추가하고 다른 컬럼·행 구조는 변경하지 않는다.

L10N 표가 없으면 기존 본문을 보존한 채 페이지 맨 아래에 다음 컬럼 순서로 하나의 표를 생성한다.

```text
구분자 | 이미지 | 국문 | 영문 | String ID
```

- Figma 프레임은 PNG 첨부로 업로드한다.
- 같은 프레임의 태그는 문구별 한 행으로 만들고 이미지 셀은 세로 병합한다.
- `구분자`는 스트링 태그 payload의 두 번째 항목이다.
- `국문`은 참조된 타겟 텍스트 값이다.
- `영문`과 `String ID`는 빈칸이다.
- 프레임은 Figma 입력 순서, 캔버스의 위→아래·왼쪽→오른쪽 순서로 배치한다.
- 같은 프레임 안의 태그는 구분자를 자연 정렬한다.

첨부 파일명은 파일 키와 프레임 노드 ID를 포함한 결정적 이름을 사용한다. 재시도 시 중복 첨부를 만들지 않고 같은 첨부의 새 버전으로 갱신한다. 페이지 본문 갱신 직전에 최신 페이지 버전을 다시 확인해 다른 사용자의 동시 편집을 덮어쓰지 않는다.

표 생성이 끝나면 작업 상태는 `영문 검수 대기`가 된다. 사용자가 영문을 작성한 뒤 같은 `String ID 생성` 버튼을 다시 누르면 기존 표 처리 흐름으로 진입한다.

## 9. 기존 표 비교와 부분 처리

기존 표는 이미지 그룹과 구분자를 기준으로 Figma 태그와 대응시킨다. 대응 후 국문은 앞뒤 공백과 줄바꿈 형식만 정규화하여 비교한다.

- Figma에만 있는 태그: `위키 행 누락`
- 위키에만 있는 구분자: `Figma 태그 누락`
- 같은 구분자지만 국문이 다른 항목: `국문 불일치`
- 잘못된 태그 locator: `Figma 태그 오류`

문제가 있는 항목만 건너뛰고 정상 항목은 계속 처리한다. 문제는 앱의 확인 필요 목록에만 표시한다. 최종 확정도 검증된 정상 항목만 JSON에 반영한다.

## 10. ReleaseDate

입력 필드가 바뀔 때 위키 페이지 제목과 Figma 파일 제목에서 `vNNMM`을 찾는다. `[v2607-10]`은 `v2607`로 처리한다.

- 위키 또는 Figma 중 하나만 있어도 자동 계산한다.
- 두 값이 다르면 위키 값을 사용하고 비차단 경고를 표시한다.
- 둘 다 없거나 업데이트 날짜를 찾지 못하면 사용자가 직접 입력한다.
- 사용자가 값을 직접 수정하면 이후 자동 계산이 덮어쓰지 않는다.

버전의 연·월을 이용해 Confluence 업데이트 페이지 `134241634`와 해당 연도 하위 문서에서 PC 업데이트 날짜만 찾는다.

## 11. String ID 결정 규칙

형식은 `FEATURE:SCREEN_TYPE_NUMBER`를 따른다. 값은 대문자이고 공백을 사용하지 않는다. 타입 후보는 기존 규칙의 `ALL`, `GNB`, `TITLE`, `BODY`, `BUTTON`, `TOOLTIP`, `FLOAT`, `ICON`, `MSG`를 사용하며 번호는 0부터 시작한다.

LLM은 위키 국문·영문, 스트링 태그 ID 힌트, Figma 파일·페이지·프레임·레이어 경로, 주변 텍스트를 이용해 피처·화면·타입 후보를 만든다. 저장 전 결정적 규칙 엔진이 형식, 기존 키, 번호와 COMMON 규칙을 최종 검증한다.

문자열 비교 단위는 JSON의 영문 `Text + Type`이다. Text는 앞뒤 공백과 줄바꿈만 정규화하고 대소문자, 문장부호, placeholder는 정확히 일치시킨다.

우선순위:

1. 동일 `Text + Type`의 기존 COMMON 키가 있으면 사용자가 피처 ID를 입력했어도 COMMON 키를 추천한다.
2. COMMON 후보가 여러 개면 가장 최신 `ReleaseDate`를 선택한다. 날짜가 같으면 String ID 오름차순의 첫 키를 선택한다.
3. 현재 피처에 동일 `Text + Type`의 기존 키가 있으면 재사용한다. 여러 개면 최신 `ReleaseDate`, String ID 오름차순으로 선택한다.
4. 기존 COMMON이 없고 동일 `Text + Type`이 `ui_common.json`을 제외한 서로 다른 피처 JSON 두 개 이상에 존재하면 새 COMMON 키를 추천한다. `ui_dev.json`과 현재 위키에서 추가 예정인 피처도 계산에 포함한다.
5. 위 조건이 아니면 피처별 신규 키를 생성한다.

기존 키를 재사용하면 COMMON 여부와 관계없이 JSON에 새 항목을 추가하지 않는다.

이미 작성된 ID 처리:

- 같은 ID와 같은 영문이면 기존 키를 재사용한다.
- 같은 ID지만 영문이 다르면 실제 충돌로 보고 같은 패턴의 최대 번호 다음 값으로 재번호화한다.
- 위키 내부에서 서로 다른 영문이 같은 ID를 사용하면 뒤쪽 항목을 재번호화한다.
- 유효하고 충돌하지 않는 사용자 편집 ID는 반복 생성 시 유지한다.
- 형식이 잘못됐거나 대상 파일을 결정할 수 없는 ID는 해당 항목을 확인 필요로 남기고 임의 수정하지 않는다.

## 12. JSON 최종 확정

`최종 확정`은 위키를 다시 조회하고 현재 String ID, 영문, ReleaseDate와 기존 JSON을 재검증한다. ID의 FEATURE가 대상 파일을 결정한다. 예: `CLAN`은 `ui_clan.json`, `COMMON`은 `ui_common.json`이다.

기존 키 재사용 항목은 JSON을 변경하지 않는다. 신규 키만 `{ "Text": <영문>, "ReleaseDate": <날짜> }` 형식으로 대상 파일에 추가한다.

모든 신규 변경 파일을 임시 파일에 먼저 작성하고 JSON 파싱과 중복 검사를 완료한다. 원본 백업은 `%APPDATA%\String-Finder\backups\<task-id>\`에 저장한다. 교체 중 실패하면 백업으로 롤백한다. 성공 후 앱에서 파일별 diff, 기존 키 재사용 수, 신규 추가 수, 건너뛴 수를 보여준다.

Git pull, commit, push는 실행하지 않는다.

## 13. 취소와 실패 처리

- 외부 조회·LLM·표 생성 준비 중 취소: 진행 중 요청을 중단하고 아직 위키나 JSON에 쓰지 않는다.
- 위키 표 또는 String ID가 이미 작성된 뒤 취소: 앱 작업 상태만 종료하고 위키 내용은 유지한다.
- JSON 교체 중: 손상을 막기 위해 취소 버튼을 비활성화한다.
- 취소 전 확인 대화상자를 표시한다.
- 항목별 Figma·위키 불일치는 부분 오류로 처리한다.
- 인증 실패, 페이지 버전 충돌, 표 구조 파싱 실패, JSON 쓰기 실패처럼 전체 결과의 신뢰성을 보장할 수 없는 오류만 해당 단계의 쓰기를 중단한다.

## 14. 검증 전략

- 스트링 태그 parser: 직접 노드, 인스턴스 경로, 잘못된 payload
- 프레임 선택: 태그 외부의 최상위 화면 프레임, 여러 태그의 프레임 중복 제거
- 위키 표: 기존 표 감지, String ID 컬럼 추가, 새 표 HTML과 이미지 병합, 본문 보존
- 비교: 정상, 위키 누락, Figma 누락, 국문 불일치의 부분 처리
- ReleaseDate: 단일 출처, 위키 우선, 수동 입력 보호
- ID 규칙: 재사용, 충돌, COMMON, 최신 ReleaseDate와 동률 결정
- JSON: 기존 키 무변경, 신규 추가, 다중 파일 롤백
- 취소와 반복 실행 상태 전이
- 타입 검사와 production build
- 패키징된 Windows 앱에서 `.env`, Figma, Confluence, 임시 이미지 정리, 최종 diff 수동 확인
